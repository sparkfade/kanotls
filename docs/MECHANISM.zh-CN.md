# KanoTLS — 内部机制参考

本文档描述 KanoTLS 的内部架构、密码学设计和流量整形逻辑。先阅读主 README 获取概览。

## 1. 握手认证嵌入

### 1.1 Noise 在 ClientHello 字段中的封装

外层 TLS ClientHello 在 TLS 1.3 预期为随机的字段中承载完整的 `Noise_NNpsk0_25519_ChaChaPoly_BLAKE2s` 初始握手载荷：

| ClientHello 字段　　　　　| 内容　　　　　　　　　　　　　　　　　 | 大小 | 编码方式　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　 |
| ---------------------------| ----------------------------------------| ------| --------------------------------------------------------------------------------------|
| `random[0..32]`　　　　　 | Noise initiator 临时 X25519 公钥 (`e`) | 32 B | 与 `derive_noise_e_mask(derived_psk, noise_tag)` 进行 XOR　　　　　　　　　　　　　　|
| `session_id[0..16]`　　　 | Noise PSK 认证的 AEAD tag　　　　　　　| 16 B | 直接复制 `psk_e[32..48]`　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　 |
| `session_id[16..24]`　　　| 连接计数器　　　　　　　　　　　　　　 | 8 B　| 与 `derive_counter_mask(derived_psk, random)` 进行 XOR　　　　　　　　　　　　　　　 |
| `session_id[24..32]`　　　| 计数器认证 MAC　　　　　　　　　　　　 | 8 B　| `derive_counter_mac(psk, random, masked_counter, random[..16])`；字节 31 低 2 位清零 |
| `key_share` (扩展 0x0033) | 独立的 TLS 层 X25519 临时密钥　　　　　| 32 B | `rand::thread_rng().fill_bytes()` — 与 Noise 密钥无关　　　　　　　　　　　　　　　　|

映射是确定性的：给定相同的 PSK 和 Noise initiator 状态，产生的 ClientHello 字段相同。服务端通过应用相同的 XOR 掩码恢复 Noise 临时密钥，重建 48 字节的 Noise init 消息（32B `e` + 16B tag），并完成 `NoiseState::read_message()`。

**多用户认证。** 服务端入站配置 `users` 列表（`{name, password}`），每个密码在启动时经 `derive_psk()` 展开为独立的 `derived_psk`。握手时服务端将每个候选 PSK 逐一与 ClientHello 校验，**顺序是计数器 MAC → 临时密钥解掩 → `read_message()` → 计数器重放 → 临时密钥重放**，首个全部通过的 PSK 即标识出认证用户（`crates/tunnel/src/server/mod.rs` 的 `authenticate_client_hello()`）。

**计数器 MAC 必须排在最前。** 它的四个输入（`derived_psk`、ClientHello 的 `random`、掩码后的计数器、`random` 前 16 字节）全部来自原始 ClientHello 字节，与 Noise 状态无关，因此可以无条件前置；而 `build_responder()` + `read_message()` 实测约 6.3–8.0 µs，counter-MAC 仅约 0.2–0.3 µs，**相差 27–32 倍**。前置之后不匹配的候选只花一次 keyed hash、不做 AEAD，于是 512 并发握手 × 50 用户的开销从约 161–206 CPU-ms 降到约 5–8 CPU-ms。这既是多用户服务器的认证加速，也堵掉一个放大型 DoS——此前攻击者用垃圾 ClientHello 就能迫使服务端对**每个**配置用户各跑一遍完整探测。

> **机制归因更正**：`Noise_NNpsk0` 的首消息模式是 `-> psk, e`，responder 的 `read_message` 只做 `mix_key_and_hash(psk)`、`mix_hash(e)`、`mix_key(e)` 加一次 16 字节 AEAD 解密——**全是对称运算，没有 X25519 纯量乘**。椭圆曲线运算发生在 `write_message`（应答侧，每次成功握手一次）。此前文档称单次探测的代价是「若干哈希加一次 AEAD 解密」，量级低估了：实际是三条 HKDF-BLAKE2s 链。识别出的用户名会附加到连接上，路由引擎可通过规则的 `auth_user` 字段按用户分流。

### 1.2 为什么使用双 Key Share？

`key_share` 扩展包含每连接独立的新鲜随机 X25519 公钥。该密钥用于与参考（伪装）端点完成可见的 TLS 握手。它与 `random` 中的 Noise 密钥**密码学独立**。这防止被动观察者通过统计测试关联两个 32 字节字段——它们来自独立的熵源（`rand::thread_rng` vs `snow::Builder::build_initiator()`）。

### 1.3 计数器防重放

64 位计数器切分为：

```
counter = (session_id << 24) | sequence
```

- **session_id**（40 位）：每次客户端重启随机生成，隔离独立会话。
- **sequence**（24 位）：每个会话内严格单调，从 1 开始。

服务端使用每个会话命名空间的**64 位滑动窗口位图**（LRU 缓存，4096 条目）。比最高已见序号新的序列推进窗口；最多落后 63 的序列在位图中检查；更旧的序列被拒绝。同一序列号永不接受两次。

独立的**临时密钥重放缓存**（LRU，65536 条目，600 秒 TTL）通过对恢复的 Noise 临时公钥建立索引来捕获完整的 ClientHello 重放。

## 2. 伪装 Profile 系统

### 2.1 Profile 结构

`CamouflageProfile` 记录了参考端点的可见 TLS 1.3 握手形态：

| 字段 | 说明 |
|---|---|
| `server_records` | 所有可见握手记录（ServerHello、Certificate、CCS 等）的原始字节 |
| `prefix_app_data_sizes` | 因太小而无法承载 Noise 载荷的早期 0x17 记录的线速大小 |
| `app_data_sizes` | 参考端点所有采样的 0x17 记录的线速大小 |
| `first_app_data_delay_us` | ServerHello 到达到首个 0x17 记录之间的**微秒**数 |
| `early_app_data_gap_us` | 连续 0x17 记录间的时间间隔（**微秒**） |
| `has_ccs` | 参考端点是否发送了 CCS 记录 |

### 2.2 启动健康检查

服务端启动时，`validate_camouflage_endpoint()` 向参考端点发送 4 次由模板实例化的新鲜 ClientHello（与客户端相同的 Firefox 模板）。每次 flight 经指纹化（random/session_id/key_share 置零，padding 扩展规范化）后，按 per-指纹 key 和指纹族 baseline key（指纹哈希的前 8 个 hex 字符）进行缓存。

### 2.3 逐连接回放

客户端连接时：

1. 通过 `stable_client_hello_fingerprint()` 对 ClientHello 进行指纹化。
2. 服务端查找最佳缓存 profile（偏好完整 profile：rank 3 = 同时具有 server_records 和 app_data_sizes）。
3. 若没有完整缓存 profile，`fetch_camouflage_flight()` 向参考端点执行实时获取（含 refresh-gate 去重）。
4. `establish_synthetic_camouflage_tunnel()`：
   - 将客户端的 `session_id` 回显到缓存的 ServerHello 中。长度不匹配说明缓存 profile 与本连接不自洽，此时拒绝握手，而不是回显一个客户端从未发送过的值（RFC 8446 §4.1.3）。
   - 用新鲜随机字节替换 ServerHello 的 `random`（若存在降级哨兵则保留）。
   - **逐连接重新生成 ServerHello `key_share`**（服务端临时 ECDHE 公钥），按组区分：X25519 与 secp256r1 用 ring 生成真实密钥对（随机字节不是合法曲线点；而随机 32 字节「X25519 公钥」有一半概率置最高位，真实 u 坐标则恒不置位）；X25519MLKEM768 的 ML-KEM-768 密文部分是密集打包，均匀随机字节即合法且分布正确。若不做这一步，缓存 profile 被逐字节回放，服务端会在每条连接上交出**同一个** ECDHE 公钥——整个缓存生命周期内至多 4 个变体、按 300–3000 秒刷新周期轮换。真实端点不可能重复公钥，因此每流只存 32 字节、两条连接即可零误报识别。遇到不支持的组时 fail closed，而不是把该指纹发出去。
   - 发送所有可见握手记录。
   - 发送前缀 0x17 记录（太小而无法承载 Noise 载荷），逐连接以 `rand::thread_rng()` 新鲜填充。
   - 发送封装在 0x17 记录中的 Noise 应答（大小匹配缓存的首个 app_data 大小，Noise 服务端公钥 XOR 掩码在前 32 字节中）。
   - 发送幽灵 0x17 记录（按缓存大小），逐连接以 `rand::thread_rng()` 新鲜填充。

> **ServerHello 之后服务端写上线的每个明文字节，都必须逐连接新鲜随机。** 这些记录冒充的是 NewSessionTicket——在 TLS 1.3 中它位于加密 record 内，线上就是均匀随机的 AEAD 密文。此前有两处违反该原则，现已移除：
>
> - 每条幽灵记录前置一个固定的 16 字节 `22 00…00`「伪造会话票据结构头部」。它是常量、是明文、且位于固定偏移，一次 16 字节 `memcmp` 即可命中，误报率 2^-128，而且在每条连接中重复最多 255 次。
> - 载荷取自一个进程级 8 MiB 熵池并循环读取，于是不同连接的载荷之间出现逐字节相同的数百字节片段。真实 AEAD 密文永不重复，这种复用让观察者能把不同流归并到同一服务端进程。实测：每连接约 1.8 KB 幽灵载荷时，约 64 条连接内即出现碰撞。
>
> `crates/tunnel/src/server/wire_tests.rs` 现在对这两条性质各有断言（无常量字节位置、跨连接无相同 16 字节窗口），回归即 CI 失败。

### 2.4 后台刷新

每个 (host, port) 对的守护进程每 300–3000 秒（随机化）使用与探测相同的 ClientHello 指纹刷新 profile。

## 3. 主动流量整形

### 3.1 设计缘由

v1.0 原始双模分布（§3.1–3.4）被动地在 `BLOCK_DATA_CAPACITY`（16382）边界上切分应用载荷，并以概率性尾部填充（80/20 抖动）包裹余量。这导致内部 TLS 明文尺寸被直接映射至外部线速记录尺寸，暴露结构指纹（例如 5000 字节的证书会生成 16382 + 16382 + 1236 = 三条记录，其尺寸对被动观察者泄露内部握手形态）。v1.1 引入**自上而下的主动 TrafficShaper**，强制每条记录的线速尺寸与应用程序载荷独立确定——明文长度不再映射至线速长度。

### 3.2 Control 类

协议帧（CMD_SYN、CMD_FIN、CMD_SETTINGS、CMD_SYNACK、CMD_PADDING）使用 `encrypt_variable_block`。控制记录的线速大小由 `control_size` 中的**状态感知采样器**确定：

- **开场序列**（`h2_opening_size`，`H2_OPENING_MAX_LEN = 3`）：**确定性**，不是抽样。
  - **C2S 共 1 条**：`SETTINGS-ACK`（33）。客户端自己的 `preface + SETTINGS + WINDOW_UPDATE` 已经作为 Flight-3 的 H2 ghost 记录发出（§3.9 的 86/92/98 行），所以控制记录流从 H2 前言**之后**开始，真实 Firefox 开场剩下的恰好就是回应服务端 SETTINGS 的那条 ACK。
  - **S2C 共 3 条**：`SETTINGS`（51 或 69）→ `WINDOW_UPDATE`（37）→ `SETTINGS-ACK`（33），三条记录一次 flush 出网（121/139 字节，一个分段）。这是 nginx/h2o 的服务端开场。
  - **不做长度随机化**，也**没有融合窗口**：真实 H2 的开场→稳态转换本来就是硬切换（发完 SETTINGS-ACK 之后 SETTINGS 永不再现），硬边界在这里是**保真**而非缺陷。唯一的变化是 SETTINGS 携带几个参数（决定 small/large 两档尺寸），由 `OnceLock` 逐**进程**固定——真实端点的 SETTINGS 内容是编译期决定的。

  此前的模型是「前 6 个控制帧各自独立地从一个含 SETTINGS 的加权池抽样」，权重使 SETTINGS 族占 0.78 ⇒ 每方向约 4.7 个 SETTINGS 形状的帧，而真实 H2 每方向只发一个；且切换点是全局常量 6，跨连接跨部署完全一致。

- **传输状态**（开场序列耗尽之后）：5 个离散尺寸（33, 37, 41, 46, 54）模拟 PING、WINDOW_UPDATE、SETTINGS_ACK 及其合并变体（**无 SETTINGS 尺寸**）。10% 的帧从截断正态的 HEADERS 分布中采样（C2S: μ=450, σ=120, [250, 800]; S2C: μ=200, σ=50, [100, 400]）。

- **承载 `CMD_SYN` / `CMD_FIN` 的记录例外**：它们改用与数据记录相同的采样器（`next_data_record_payload`），**不取控制离散池**。原因见 §9.3 的实测：控制池的 5 个尺寸全部落在 `L1`（≤160），而关流时本端 FIN 与对端 FIN 各占一个分段、紧跟响应体最后一段之后 ⇒ 实测**每 4~5 次关流就精确复现 `(−L4, L1, −L1)`**。真实 H2 里开流是 `HEADERS`、半关是挂在 `DATA` 上的 `END_STREAM`，都不是孤立小帧。
  `CMD_SYNACK` **刻意不在此列**：把它放大会让服务端开场 flight 超过 1211 字节，与客户端合法的 33 字节 SETTINGS-ACK 配成 `(L2, −L4, L1)`（判别力 7.226）——SYNACK 的「小」在出生窗口内是保护性的。

每个控制帧递增 TrafficShaper 内部的控制帧计数器（`note_control_frame()`），影响 Markov 状态机的握手到传输转换（§3.4）。

### 3.3 TrafficShaper 架构

`TrafficShaper`（每连接实例，由 `SessionWriter::run` 持有）拦截所有应用数据（PSH）写入。全新的 `drive_shaper` 循环替代了旧的 `write_half.write_all(pending)` 全量倾倒方式：

1. **策略查询**: `shaper.next_data_policy(pending_len)` 返回 `ShapePolicy { target_wire_len, delay, fake, allow_full_block }`.
2. **切分截断**: 若 `pending` 超出 `target_wire_len` 所能承载的载荷容量，仅取走对应字节数，其余保留在 `pending` 中供后续迭代处理。如 5000 字节待处理 vs 800 字节目标 → 发出 800 字节记录，保留 4200 字节。
3. **精确填充**: 若 `pending` 小于目标容量，以零字节填充至精确 `target_wire_len` 后发出。
4. **加密**: `SnowyStream::prepare_data_record(slice, target_wire_len)` 加密唯一一条线速尺寸等于 `target_wire_len` 的记录。
5. **Flush** + **delay** + **advance**: 记录刷新，若 delay 非零则注入 `tokio::time::sleep(delay)`，随后 shaper 的包序列号和 Markov 状态推进。
6. **虚假交互**: 若策略携带 `fake`，在当前切片发出后向控制队列排队一个 `CMD_PADDING` 请求帧。

以上抹除了被动尺寸痕迹包络：同一应用写入在不同策略下产生完全不同的记录边界，仅取决于 shaper 策略而非内部载荷结构。

### 3.4 Markov 宏状态机

shaper 维护三个覆盖连接全生命周期的宏状态（无硬切分"前 N 包"断崖）：

| 状态　　　　　　　　　 | 尺寸策略　　　　　　　　　　　　　　 | 延迟 | 说明 |
|---|---|---|---|
| `HandshakeShaping`　　　 | 最小拟合（精确匹配载荷）　　　　　 | 无 | Noise 握手阶段；紧密耦合以避免影响认证组帧。 |
| `InteractiveControl`　　| 复用 `control_size` HTTP/2 离散 + HEADERS 分布采样 | 15% 概率对数正态 IAT | 模拟 Web 应用请求/响应模式，记录尺寸可变。 |
| `AsymmetricBulk`　　　　 | 满载 MTU 锚定记录（`max_data_record_wire_len` ≈ 16406） | 无 | 持续大流量传输；解除碎片化封顶，将尺寸锚定至 Web 组帧边界。 |

**转换逻辑**：每次发出包后，通过**概率平滑**评估状态转换。概率值 `p_bulk = pending_len / max_pending_flush_size` 驱动转换：几乎满载的待发送缓冲区强力推动进入 `AsymmetricBulk`，而接近排空的缓冲区则推动退出至 `InteractiveControl`（退出概率上限 85%）。这替代了 v1.1 的确定性阈值，通过连续概率渐变避免状态边界振荡。

### 3.5 声明式流量脚本引擎

流量脚本引擎为握手完成后的数据包序列提供确定性、可回放的控制，包括记录尺寸、记录间延迟、以及对端交互信号。它由用户提供（或嵌入式默认）的规则列表驱动，规则按 `packet_seq % 规则数` 循环应用，直到 `packet_seq` 达到脚本的 `stop` 计数（默认等于规则数）。这使得操作者可以预编程一条模拟已知目标应用（如 TLS 加密的视频流或 Web 浏览会话）的包尺寸序列，而不将记录尺寸耦合至实际隧道载荷。

**规则结构：**
```
ScriptRule { len_lo, len_hi, delay: DelaySpec, expect_responses: u8, fake_jitter: i32 }
```

| 字段 | 含义 |
|---|---|
| `len_lo`..`len_hi` | 该记录中嵌入的**应用内容字节数**，从区间内均匀随机采样。Shaper 计算 `target_wire_len = MIN_DATA_WIRE_LEN + (len_lo..len_hi)`，按该精确线速尺寸填充并加密。真实待发送数据最多消耗 `len_lo..len_hi` 字节；若积压少于目标，由零字节填充补齐；若积压更多，仅切走一块，余量保留供后续迭代。 |
| `delay` | `DelaySpec::None`（零延迟）或 `DelaySpec::LogNormal{mu_ms, sigma_ms}`（从拟合对数正态分布采样的记录间暂停）。详见 §3.6。 |
| `expect_responses` | 若 `> 0`，发送方在 **Control** 通道上排入一个 `CMD_PADDING` 请求（opcode 0x08）。对端解码请求后，向发送方回吐 `M` 个独立拆分的应答帧（§3.8）。该字段设为 `0` 表示普通单向数据规则。 |
| `fake_jitter` | fake 响应的落点抖动：规则每次触发时，从 `[min(0,k), max(0,k)]` 区间内相对触发记录均匀采样一个偏移。负偏移在触发记录**之前**发出请求（归于前一条记录的槽位）；零固定于触发记录；正偏移延后发出，待目标记录发出时释放（脚本达到 `stop` 时全部剩余强制释放）。该机制将掩护帧簇与其触发记录解相关。 |

**脚本生命周期与融合窗口：**

脚本运行 `stop` 个数据包（`stop` 默认等于规则数；更大的 `stop` 会重复循环规则）。最后一个脚本包发出后，引擎进入长度为 `SCRIPT_BLEND_WINDOW = 6` 包的**平滑融合窗口**。在此窗口内，切入 Markov 状态机（§3.4）的概率从 0% 线性渐变至 100%，消除 "前 N 包后突变" 的硬切分断崖，产生在线速尺寸分布上不可指纹的平滑切换。

融合窗口结束后，TrafficShaper 的 Markov 状态机接管连接剩余生命周期。Markov 转换参数无配置暴露——它完全由待发送缓冲区压力通过概率 `p_bulk` 渐变推导（§3.4）。

**脚本后整形开关（`post_script_shaping`）：** 可选配置字段 `session.post_script_shaping` 选择脚本用尽后的行为。默认 `"markov"` 如上所述（融合窗口 → Markov 机）。`"off"` 关闭脚本后的全部整形：`packet_seq` 达到 `stop` 后，后续每条记录精确承载当前积压载荷（线速尺寸 = 积压 + 固定 record 开销），零延迟、无 Fake 帧、无融合窗口——从此刻起明文尺寸直接映射至线速尺寸。两种模式下 bulk fast path 与 bulk 迟滞（§3.4）均保持优先。除 `"markov"`/`"off"` 外的取值在启动时触发非致命警告并按未设置处理。

**数据包收发示例——客户端→服务端，3 规则脚本：**

假设 `traffic_script` 内容：
```json
"traffic_script": [
  "0=L:200-250,D:0,F:0",
  "1=L:300-400,D:2.0-0.5,F:0",
  "2=L:180-220,D:1.5-0.6,F:0"
]
```

实际应用数据积压：6000 字节。

| 包序号 | 规则 | 采样 `len` | 消耗真实数据 | 线速 record 尺寸 | 发出后行为 |
|---|---|---|---|---|---|
| 1 | 规则 0 | 215 | 215 字节（来自积压） | `MIN_DATA_WIRE_LEN + 215`（≈ 239） | Flush。无延迟。`packet_seq` → 1。剩余积压：5785。 |
| 2 | 规则 1 | 362 | 362 字节 | `MIN_DATA_WIRE_LEN + 362`（≈ 386） | Flush。`sleep(log_normal(2.0, 0.5))`。随后：在 Control 通道排入 `CMD_PADDING(flag=0, m=1)`。剩余积压：5423。 |
| 3 | 规则 2 | 197 | 197 字节 | `MIN_DATA_WIRE_LEN + 197`（≈ 221） | Flush。`sleep(log_normal(1.5, 0.6))`。剩余积压：5226。 |

第 3 包后脚本耗尽。第 4–9 包在**6 包融合窗口**中发出：每包有递增概率（≈17%, 33%, 50%, 67%, 83%, 100%）由 Markov 机控制而非循环脚本。第 10 包起完全由 Markov 控制。

**服务端在线速上看到的内容（以第 2 包序列为例）：**

1. 服务端收到线速尺寸 ≈ 386 字节的 0x17 record → Noise 解密 → 明文 `[len_prefix(2B) | 362B payload | padding | 0x17]` → 交付 362 字节至对应 stream。
2. 经对数正态采样暂停（例如 1.8 ms）后，服务端收到一条**Control 类 0x17 record**，内含 `CMD_PADDING` 请求（`cmd=0x08, flag=0, m=1`）。
3. 服务端帧处理器立即向客户端回吐 1 条 `CMD_PADDING` 应答帧（`cmd=0x08, flag=1`，零填充垃圾字节），通过 Control 通道发出。该应答帧为独立的 0x17 record，尺寸从 Control 类传输态池中采样（33–82 或 124–824 字节，§3.2）。
4. 应答帧永不递交至任何 stream——在 session 帧处理层解码后静默丢弃，仅作为掩护流量打破一问一答对称性。

脚本源为嵌入式默认值（6 条规则，见 §8），可通过 `traffic_script` 配置字段覆盖。配置值为 JSON 字符串数组：一个可选的 `stop=N` 控制条目，后跟带索引的规则 `i=L:...,D:...,F:...`（索引必须与规则的 0 基位置一致）。配置验证在启动时解析该数组；任一格式错误的条目触发非致命警告并回退至嵌入式默认脚本。

`L` 字段除 `lo-hi` 外还接受 `base?range` 语法：在 shaper 构建时每连接采样一次 `base + U[0, range]`，该值在此连接的生命周期内固定。解析完成后，每个连接在 `TrafficShaper::new` 中对脚本做随机化：规则顺序按随机偏移轮转，且每条规则的长度区间乘以独立的 U[0.85, 1.20] 采样（钳制至 ≥ 1 且 ≤ 数据 record 容量），因此「位置 → 尺寸」映射跨连接不恒定。

格式示例：
```json
"traffic_script": [
  "stop=4",
  "0=L:200-250,D:0,F:0",
  "1=L:300-400,D:1.5-0.5,F:2?-1"
]
```

### 3.6 IAT 延迟建模

记录间延迟的非零延迟规格如下（`DelaySpec::None` 表示零延迟）：

- **`DelaySpec::LogNormal { mu_ms, sigma_ms }`**：对数正态分布（Box-Muller 正态采样 → `sample_log_normal(mu, sigma)` → `Duration::from_micros`），匹配真实 TCP 包间时距的右偏正定分布，优于均匀或指数抖动。

Markov `InteractiveControl` 状态以 15% 概率施加延迟；脚本引擎按规则逐条施加。`AsymmetricBulk` 状态零延迟（背靠背发送）以保持吞吐量。

### 3.7 记录填充

整形数据记录与 `CMD_PADDING` 伪造载荷中的填充字节一律为**零**——这正是 RFC 8446 §5.4 为 TLS 1.3 record padding 规定的取值。

此前的设计从一个 8 MiB CSPRNG 熵池取这些字节，理由是填充必须「与真实 AEAD 密文密码学同构」。该论证不成立：这些字节全部位于 `encrypt_variable_block` 的**明文**一侧，随后由 ChaCha20-Poly1305 加密，观察者看到的密文对任何明文输入都是均匀随机的。熵池在这些位置没有任何收益，代价却是每条记录一次跨 8 MiB 的 cache-hostile 拷贝，外加一个全局争用的原子游标。该模块已删除。

真正需要随机性的是合成伪装回放（§2.3）中服务端以明文写上线的字节；那些字节逐连接取自 `rand::thread_rng()`。

### 3.8 虚假交互引擎 (CMD_PADDING)

`CMD_PADDING`（操作码 0x08）是 session 级别控制帧，载荷格式为：

```
| flag(1B) | m(1B) | junk(零填充) |
  flag = 0 → 请求　　 1 → 应答
```

- **请求**（`flag=0`）：由发送方在脚本规则或策略指定 `expect_responses = M` 时在**Control**队列（优先）上发出。伪造字节为零（随帧一并加密）。
- **应答**（`flag=1`）：接收方解码请求后回吐 `M` 个**独立拆分**的应答帧，每个是独立的 Control 记录。尺寸按 H2 角色确定（请求为 SETTINGS 尺寸 → 回 33；PING 尺寸 → 回 41；HEADERS 量级 → 回响应量级；索引 >0 的一律 37 = WINDOW_UPDATE），**不再从请求的载荷长度派生**——那会制造「请求尺寸 → 应答尺寸」的相关性。`M` 的上限从 16 降到 **2**：H2 语义下一次 PING/SETTINGS 恰好换一个 ACK，WINDOW_UPDATE 不换应答，唯一站得住脚的第二帧是接收方本来就会发的窗口更新。

> **内嵌默认脚本已不再使用本机制**（全部规则 `F:0`）。`F:1` 会在数据记录 2 和 4 注入 PING/PING-ACK 对，而真实 H2 的 PING 是 30–150 秒间隔的保活帧；在连接开场几百毫秒内打两对 PING，把尺寸做得越像 PING 反而越容易被识别，若紧跟一个下行 burst 更会构成 `(−L4, L1, −L1)`。用户脚本仍可使用 `F:m`（不静默忽略），但配置校验会给出警告。
- 应答帧永不递交到任何数据流——在帧处理层静默丢弃（作为读取活动以保活空闲超时计时器）。
- 请求与应答的伪造字节均为零；它们位于 AEAD 的明文一侧，内容在线上不可见。

### 3.10 反 TLS-in-TLS 的三层结构

本节描述针对 USENIX Security 2024 那套「嵌套 TLS 握手指纹」检测器（§9 通篇引用的那篇）建立的机制。检测器只取**外层握手之后的前 25 个承载数据的 TCP 包**，并**只在连接出生时判一次**（§9.1）。

#### 保真层（观测窗口内）

- **连接的首条整形数据记录**取 `FIRST_RECORD_PAYLOAD_LO..HI` = 152..248 载荷 ⇒ 线速 176..272 字节，**严格小于 300**，且抢在流量脚本之前（仅 C2S 方向）。窗口内保持变化而非取定值：真实 H2 的首个 HEADERS 尺寸随请求而变，取定值会换来一个跨连接稳定的整数。
- **`quiet_gap`：首条记录发出后让出方向。** burst 只能由方向改变或 ≥3×RTT 的间隔打断（§9.2），所以写方必须真的安静下来——`wait_for_peer_turn` 等待对端到达，上界 `PEER_TURN_MAX_WAIT = 300 ms`。这正是论文所要求的 "buffer application data when the scheduler demands quiet time"。代价是每条隧道连接一次 +1 RTT（仅 `packet_seq == 0`），由连接池摊销。**仅 C2S**：Figure 8 测的是客户端的首个 burst，让服务端也暂停是 nginx 不会有的形态。
- **服务端在解码客户端 `CMD_SETTINGS` 后立即发出 nginx/h2o 形态的开场 flight**（§3.2），客户端以 33 字节 SETTINGS-ACK 应答。这比等待 SYNACK 更快（SYNACK 要等 DNS + connect，10–100 ms），且是帧层应答、亚 RTT。
- **合成共存流引擎**：论文指出多路复用的有效性完全依赖**活跃**的共存流，单流场景下与非多路复用一样暴露。客户端因此维持一条低速的合成 H2 请求/响应交换（HEADERS 尺寸的控制记录，`m=1`，对端回一条响应量级记录）：开场 `U{1,2,3}` 次、中位数约 30 ms（落在窗口内），随后浏览量级（中位数约 20 s，重尾，上限 300 s）。门控：仅客户端、`!post_script_off`、**对端已说过话**（否则合成请求会并入首个上行 burst 撑破 300 字节上界）、且仍在开场窗口内或至少有一条流打开。最后一条门控是刻意的——完全空闲的 H2 连接**应当**被空闲超时拆除，用假帧人工吊着本身就是特征。

#### 永久层（连接终生，近乎零成本）

1. **数据记录永不落 `L1`**（线速 ≤160）。`markov_policy` 与 `script_policy` 都受此约束；后者是硬钳制，因为配置期的 lint 警告拦不住已经发出的记录（§9.6）。
2. **记录尺寸不得是积压大小的确定性函数**——但**真实 bulk run 的精确尾包是保真的**（真实 TLS 写 100 KB = 6 条满记录 + 1 条精确尾包）。边界即 `bulk_run` 谓词：同一次 drain 内已发出过满容量记录时，尾包只多给出 `n mod 16384`；没有该前缀时 `n mod 16384` **就是** `n`，也就是内层协议的消息长度。**这条保护的是内层消息长度，不是窗口范围的。**
3. **flush 合并**：control/bulk 通道都空时才冲刷，否则并进下一次 `write()`。TCP_NODELAY 下 flush 边界就是分段边界，也就是分类器观测的单位；真实 NSS/BoringSSL 会把 nghttp2 队列里的全部内容排进一次 `write()`。实测对论文特征**无可测量收益**（§9.8），保留是因为它更接近真实实现。
4. **承载 `CMD_SYN` / `CMD_FIN` 的记录不取控制离散池**（§3.2 末段）。

#### 窗口外放松

观测窗口结束后（度量用 `flush 次数 + inbound.arrivals()`，是双向数据包数的**下界**，所以只会更晚放松），`markov_policy` 的 15% 对数正态延迟注入在 `POST_WINDOW_RELAX_BAND = 12` 包内线性衰减到零。衰减的是 **Bernoulli 触发概率**，不是 `mu`/`sigma`——形状与位置在真实实现里是常量。

**必须有衰减带、不许断崖**：整形在第 N 包戛然而止会在 N±5 处留下分布断层，那是本项目已解决过两次的同一类问题（脚本融合窗口、control 态开场序列）。

实测收益：960 KB 的 8 KB 写入从 876 ms 降到 86 ms（约 10×）。**中等积压的尺寸切分不放松**，理由见永久层第 2 条。

## 4. Session 多路复用

### 4.1 帧协议

每帧 7 字节头部：

```
| cmd (1) | stream_id (4, BE) | data_len (2, BE) | payload (0–65535) |
```

| 命令　　 | 操作码 | 用途　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　 |
| ----------| --------| --------------------------------------------------------------------------|
| SYN　　　| 0x01　 | 打开流　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　 |
| PSH　　　| 0x02　 | 推送数据　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　|
| FIN　　　| 0x03　 | 关闭流（半关闭）　　　　　　　　　　　　　　　　　　　　　　　　　　　　|
| SETTINGS | 0x04　 | Session 能力协商　　　　　　　　　　　　　　　　　　　　　　　　　　　　 |
| SYNACK　 | 0x07　 | 流打开确认　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　|
| PADDING　| 0x08　 | 虚假交互引擎（§3.8）；请求/应答掩护帧　　　　　　　　　　　　　　　　　|

### 4.2 流水线流打开

客户端流打开将 `[SETTINGS] [SYN] [PSH(target)] [PSH(data)]` 融合为一次 control-class coalesced write flush。全新 session 的首个 stream 通过 `DeferredUnsent` 状态延迟 SYN 发送——SETTINGS 帧（保存在 `PendingClientSettings` 中）和 SYN 帧被缓冲在 `Stream` 对象中而不发送。首次 `write()` 调用时，`write_gather_open()` 通过 `PendingClientSettingsGuard` 取出 SETTINGS 帧，置于 SYN 之前，然后追加目标和数据 PSH 帧。全部帧经由 `coalesce_encoded_frames` 压缩后，通过单次 `submit_write_packets`（`FlushBehavior::Immediate`）发出，完成单次合并写入。

服务端在验证目标、解析 DNS、建立中继连接之后才发送 SYNACK。因此 SYNACK 确认的是真实可达性——不仅仅是流接受。

### 4.3 空闲拆除

Session 读取循环（`run_read_loop`）使用 pinned `tokio::time::sleep` 定时器（`idle_timeout_secs`，默认 **75 秒**，来自配置，**不加抖动**）。每次成功读取时，定时器重置为 `now + idle_duration`。若定时器触发时无活跃流、无待处理入站流、无待打开流（`is_idle_timeout_eligible()`），Session 优雅拆除：发送 Noise 加密的 TLS `close_notify` 告警（0x15），随后 TCP FIN。不发送应用层心跳——内核 TCP keepalive 作为死端检测机制，取值对齐 **Firefox 的默认值：空闲 600 秒、间隔 1 秒、4 次探测**（`network.tcp.keepalive.idle_time / retry_interval / probe_count`），**不加抖动**：Firefox 对所有 socket 设同一组值，逐连接抖动会让「同一客户端的不同连接有不同 keepalive 周期」，而真实浏览器不会。

代价：死端检测窗口从约 150 秒变为约 604 秒。一个真正失联（无 FIN/RST）且仍持有活跃流的对端会挂约 10 分钟。无活跃流的连接不受影响——服务端 75 秒空闲拆除与客户端池的空闲回收会先把它们收走。

**H2 层的存活探测另有一套**（§4.4）：客户端按 **58 秒无对端到达**触发一次 `PING`（Firefox `network.http.spdy.ping-threshold` 的默认值），服务端从不主动发 PING（nginx 不发），只回 PING-ACK。且连接仍处于论文观测窗口（前 25 个承载数据的包）之内时**抑制** PING——窗口内的 `(+41, −41)` 对若紧跟一个下行 burst，就构成 `(−L4, L1, −L1)`。

**客户端连接池的空闲回收取 115 秒**（Firefox `network.http.keep-alive.timeout` 的默认值；115 而非 120 是因为它刚好卡在常见的 2 分钟 NAT 状态超时之下），**不加抖动**。于是先关闭的一方是**服务端**（75 秒），这与真实场景一致——通常是服务端按自己的 `keepalive_timeout` 关掉空闲连接。

服务端的 75 秒**不加抖动**，取自 nginx `keepalive_timeout` 的默认值。此前是 45 秒 ± 10% 抖动：抖动违反原则 2（真实 nginx 的 `keepalive_timeout` 是精确常量），而 45 不对应任何真实服务器的默认值。选 `keepalive_timeout`(75 s) 而非 `http2_idle_timeout`(3 min)，是因为后者**自 nginx 1.19.7 起已作废**，官方文档原文：「This directive is obsolete since version 1.19.7. The `keepalive_timeout` directive should be used instead.」⇒ 今天任何一台可供审查者对照的 nginx，其 H2 空闲连接走的就是 75 秒。75 < 115 也保住了「先关的一方是服务端」这条不变量。池的 `soft_ttl` 取 3600 秒，对齐 nginx `keepalive_time` 默认 1 小时的同一语义；它现在的角色是资源兜底而非行为伪装（正常使用下连接总是先因空闲或服务端关闭而消失，该值不可观测）。

**优雅拆除的线上序列是 `[GOAWAY 41 字节][close_notify 24 字节]`**，两条独立 flush，对应真实端点的 `SSL_write` + `SSL_shutdown` 两次写。此前只发一条 close_notify，前面没有任何控制尺寸的记录——而真实 nginx/Firefox 关闭 H2 连接必有 GOAWAY。GOAWAY 最小帧载荷（9 帧头 + 4 last_stream_id + 4 error_code = 17 字节）与 PING 相同，故复用 `PING_WIRE = 41`。

> **仅服务端生效**：客户端 Session 的空闲生命周期由连接池的 idle drain / soft TTL 统一驱动，`run_read_loop` 中该分支在客户端侧通过 `idle_teardown_enabled = !is_client` 屏蔽。

## 5. 防主动探测

### 5.1 解密失败

当收到的 0x17 记录 Noise AEAD 解密失败（`read_message` 返回 `Err`）时，隧道**不会**发送任何告警。取而代之：

1. 立即将 `close_notify_written` 设为 `true`，防止正常的 `close_notify` 被发送。
2. 返回 `InvalidData` IO 错误。
3. Session 读取循环收到错误后拆除 TCP 连接。
4. 不会向对端写回任何字节——连接静默关闭。

对端观察到的要么是 TCP FIN，要么是 RST（取决于操作系统），无 TLS 层告警载荷，阻止了依赖区分告警类型的主动探测。

### 5.2 Pre-Auth 回落

Noise 认证提交之前的**每一种**失败，都会把客户端流量透明转发到伪装端点。对于输入驱动的失败，这是唯一的可观测结果，且各类输入之间完全一致：

| 输入 | 可观测结果 |
|---|---|
| 非 TLS 首记录（`GET / HTTP/1.1` 等） | 透明转发 |
| 认证失败（PSK / MAC 错误、重放的 ClientHello） | 透明转发 |
| 缺失 SNI / SNI 不匹配 | 透明转发 |
| 记录头声明长度超限 | 透明转发 |
| 发送不足 5 字节，或记录截断/挂起 | 转发**恰好收到的那些字节** |

两条对抗探测的关键性质：

- **交给转发的缓冲只含客户端真实发送过的字节。** 此前的实现会先按声明长度 `resize(len, 0)` 预填零再读，于是一个挂起的 ClientHello 会被零填充到「完整」后转发给伪装端点——真实站点随即收到一个客户端从未发出的请求并回以告警。
- **任何输入都无法翻转行为。** 此前有两条 fail-closed 路径，各自 5 字节即可稳定触发：声明长度超限时瞬时关闭（且接收队列尚有未读数据，`close(2)` 发出的是 RST 而非 FIN），什么都不发时在恰好 T+10.000 秒得到静默 FIN。两者现在都走转发。

初始记录的截止时间是**两个固定常量**，按「是否已收到任何字节」选择：零字节 **2 秒**、已收到部分记录 **5 秒**（后者自 accept 起算，分片的 ClientHello 不会因此只剩 3 秒）。

**这里刻意不做随机化。** 真实 nginx 的 `client_header_timeout` 是一个精确常量，随机化我们自己的超时本身就是判别特征（§9.0 原则 2）。目标不是让超时看起来随机，而是让它**不可观测**：读超时后走回落转发，探测者观察到的关闭时刻 = 我们的超时 + 上游超时；把我们那一项压到远小于上游超时，上游的真实常量就占绝对主导，我们的贡献沉到 RTT 噪声以下。此前的 8–15 秒**整秒**采样既叠加了可测偏移，又只有 8 个离散取值。

转发本身双向传播半关闭（不转发 `shutdown(SHUT_WR)` 会让上游一直挂到它自己的 `keepalive_timeout`，与直连行为可区分），并且仅在两个方向都持续 300 秒无流量后才终止——该值远大于常见上游空闲超时，因此正常情况下总是上游先关闭、本上限不可观测；它的唯一作用是防止永久静默的连接把 permit 与 fd 钉死。

转发受以下限额约束：

| 限制 | 值 |
|---|---|
| 全局并发回落 | 512（固定值） |
| 每 IP 并发回落 | 16（固定值） |
| 回落连接超时 | 3 秒（固定值） |
| 并发握手中连接数 | 512（固定值） |

**限额耗尽时**连接无法转发，统一走唯一出口 `emit_indistinguishable_close()`：

1. 关闭前先有界排空接收队列（上限 64 KiB / 200 毫秒），使关闭恒为干净 FIN。不排空时 `close(2)` 会在 FIN 之后再发 RST，于是「探测者发过数据」与「什么都没发」得到不同的关闭序列——仅凭一条连接即可据此分类服务器。
2. 排空之后**立即关闭**，不做任何延迟。

   此前是随机等待 200–3000 毫秒。那个延迟违反原则 2：真实服务器不会在均匀随机延迟之后关闭。对齐到 `pre_auth_fallback_connect_timeout_secs`（3 秒）同样不对——3 秒是**我们自己**的常量而非任何 nginx 默认值（`proxy_connect_timeout` 默认 60 s），且真正因「连不上上游」到达这里的两条子路径**本来就已经花掉了那 3 秒**，再叠一次得到 6 秒；其余子路径（握手并发限额、回落限额、活动会话限额）根本没尝试过上游。

   诚实的模型是「服务端此刻没有容量」，而真实 nginx 在这个模型下给出的正是 accept 之后立即关闭：`worker_connections` 耗尽时 nginx 会 accept 再 `ngx_close_accepted_connection()`，客户端观察到一个几乎瞬时的干净 FIN。附带收益：被拒连接不再在服务端**已经没有容量**时额外占用 0.2–3 s 的 fd 与一个连接名额——那原本是一个正反馈。

**单 IP 累计速率限额已删除。** 此前的规则是「3600 秒窗口内回落 112 次 → 300 秒冷却」，冷却期内停止转发。它必须删掉，因为它恰好制造了本节声称不存在的东西：不需要构造任何特殊输入，**113 条普通 TCP 连接**就能让该 IP 进入 300 秒窗口，期间每条连接都落到不转发分支上；而暴露的差异是**内容级**的（第 1 条连接发 `GET / HTTP/1.1` 拿到伪装站点真实的 HTTP 响应，第 114 条拿到静默关闭），**任何关闭姿态的整形都掩盖不了**。阈值本身也可被二分精确测出，而真实 nginx 没有任何「同一 IP 连满 N 次就停止服务 300 秒」的默认行为。

> **关于「探测者无法触发这条分支」的准确表述。** 这条分支只在限额耗尽时抵达，而**单条连接的内容**无法触发它。但它并非完全不可达：单 IP 并发回落上限是 16，探测者开 16 条慢速回落连接并**持有**（permit 要等中继结束才归还），第 17 条就会落到这里。与已删除的冷却相比，区别在性质——冷却是**持久有状态**的（300 秒内稳定取样窗口），并发限额是**瞬时且负载相关**的，且探测者必须同时对伪装端点维持 16 条连接。诚实的说法是：**触发它需要探测者主动占用限额槽位，而不是选择某种输入。** 这些槽位是**无记忆**的——一旦释放行为立即恢复，服务端不保留任何跨时间状态；而已删除的冷却会在探测者离开后仍维持 300 秒的差异行为。
>
> 但还有一处需要如实记下：**单 IP 并发上限是这里唯一与真实 nginx 默认行为不完全对齐的维度。** nginx 的 `worker_connections` 是全局的；`limit_conn` 才是按 key 的，但它默认关闭、且触发时回的是 503 页面而非静默 FIN。所以一个同时持有 17 条连接、并用第二个 IP 做对照的探测者，确实能发现一点东西。两个显而易见的缓解各自都在换一个问题（把 16 提到 512 会让单个 IP 饿死全局池；去掉单 IP 上限则更贴近 nginx 的全局耗尽语义，却会把**其他**客户端推进这条分支），因此保持现状并记录在此。

## 6. 指纹预设

`fingerprint` 配置字段选择 ClientHello 生成策略：

| 预设　　　　　　　　　　　　　| 来源　　　　　　　　　　　| 加密套件顺序　　　　　　　　　　　　　　　　| Key Share 组　　　　　　　　　　　　　　　 |
| -------------------------------| ---------------------------| ---------------------------------------------| ---------------------------------------------|
| `firefox`　　　　　　　　　　 | 捕获的 bootstrap hex blob | AES-128-GCM, ChaCha20-Poly1305, AES-256-GCM | X25519MLKEM768, X25519, SECP256R1　　　　　 |

`firefox` 是唯一受支持的取值（亦为默认值）；其他 `fingerprint` 取值在配置校验时直接报错。该预设精确保留捕获的记录形态（扩展顺序、填充、记录长度），并对所有模板（内嵌或 `template_path` 自定义 hex）在加载时统一执行两项规范化：

1. **不剥离任何扩展。** 上线的扩展类型列表与捕获的真实 Firefox **逐项相同**，共 15 个：
   `0000 0017 ff01 000a 000b 0010 0005 0022 0012 0033 002b 000d 001c 001b fe0d`，
   ClientHello 总长回到 1884 字节。

   此前存在一张剥离表 `[0xFE0D, 0x014A, 0x0119, 0x001C, 0x0022]`，实际从捕获模板中删掉了
   `record_size_limit`(0x001C)、`delegated_credentials`(0x0022) 与 ECH(0xFE0D) 共 305 字节，
   使 JA3/JA4 的扩展列表**不对应任何已发布的 Firefox 版本**（15 个扩展变 12 个）。
   其中 `0x0119` / `0x014A` 在模板里根本不存在——它们是把 ECH 头部
   `fe 0d 01 19 | 00 00 01 00 01 4a 00 20 …` 当作三个扩展来走的**解析错误**：
   `0x0119` = 281 是 ECH 的 `extension_length`，`0x014A` 横跨 `config_id=0x4a ‖ enc_len=0x0020`。
   剥离机制本身保留（参数化），作为中和自定义模板中恶意扩展的唯一手段。

2. **ECH 逐连接刷新而非剥离。** 捕获的是一个 GREASE ECH（`type=0`，HPKE kdf/aead 均 `0x0001`）。
   整份重放会变成 281 字节的跨连接常量，因此每条连接重新生成三个变量字段：
   `config_id`(1 B) 随机、`enc`(32 B) **均匀随机字节**、`payload`(239 B) 随机；
   `type`、`cipher_suite` 与**全部长度字段**保持恒定。

   `enc` 必须是随机字节而**不是**真实 X25519 公钥——捕获样本的 `enc[31]` 最高位为 1，
   而真实 X25519 公钥该位恒为 0，证明 NSS 对 GREASE ECH 就是填随机字节。详见 §9.5。

   ⚠️ 与之强耦合：`stable_client_hello_fingerprint` 必须把这三个字段一并归一化，
   否则每条连接指纹不同 ⇒ 伪装 profile 缓存退化成每连接一条 ⇒ 每条客户端连接
   都触发一次对伪装端点的实时拉取。

3. **X25519 密钥每连接生成一个、写入两处。** `key_share` 中 X25519(0x001d) 份额与
   X25519MLKEM768 混合份额尾部 32 字节在真实 Firefox 中**逐字节相同**
   （NSS 3.103, Bug 1902119）。两处各生成独立密钥会制造一个比它修掉的更强的判别器
   （单连接、零误报的 32 字节 memcmp）；填随机字节则违反「真实公钥最高位恒为 0」。详见 §9.4。

4. **结构合法的 X25519MLKEM768 份额**：每条连接重新生成 1216 字节混合份额——768 个系数从
   [0, 3329) 均匀采样（与真实 ML-KEM.768 ek 同分布），随后是 32 字节 rho 种子与上述复用的
   X25519 公钥。支持 ML-KEM 的服务器（OpenSSL 3.5+）会在解码时校验系数范围，对随机垃圾回
   `illegal_parameter`。

5. **P-256 辅助份额是真实曲线点**（ring 生成），失败即 fail closed，不回退随机填充。

可通过 `template_path` 用自定义 ClientHello hex 文件覆盖内嵌 Firefox 模板，规范化同样生效。

## 7. 错误处理状态机

探测者能通过选择输入抵达的每一条分支，最终都落在透明转发上。唯一不抵达伪装端点的出口以限额耗尽为前提，任何输入都无法按需触发。

```
                          TCP 连接被 accept
                                      │
                        ┌─────────────┴──────────────────────┐
                        │ 握手限额尚有余量？                 │
                        └─────────────┬────────┬─────────────┘
                                  是  │        │ 否
                                      │        ▼
                                      │   emit_indistinguishable_close
                                      │   （排空后立即 FIN）
                                      ▼
                  读取初始记录（零字节 2 秒 / 已收到部分 5 秒，均为常量）
                                      │
                        ┌─────────────┴──────────────────────┐
                        │ 是完整的 0x16 记录？               │
                        └─────────────┬────────┬─────────────┘
                                  是  │        │ 否 — 非 TLS 类型、
                                      │        │ 声明长度超限、超时、
                                      │        │ EOF、不足 5 字节
                                      │        ▼
                                      │  Pre-Auth 回落
                                      │  → 透明转发**恰好收到的**字节
                                      ▼
                          Noise 认证 + 计数器重放 + MAC
                          （单次原子检查）
                                      │
                        ┌─────────────┴──────────────────────┐
                        │ 全部通过？                         │
                        └─────────────┬────────┬─────────────┘
                                  是  │        │ 否
                                      │        ▼
                                      │  Pre-Auth 回落
                                      │  （覆盖 Noise、计数器
                                      │    MAC 与重放）
                                      │
                        ┌─────────────┴──────────────────────┐
                        │ SNI 与伪装主机匹配？               │
                        └─────────────┬────────┬─────────────┘
                                  是  │        │ 否
                                      │        ▼
                                      │  Pre-Auth 回落
                                      │
                                      ▼
                             提交计数器重放
                                      │
                                      ▼
                              合成伪装回放
                                      │
                                      ▼
                           Noise 传输态建立
                                      │
                        ┌─────────────┴───────────────────────┐
                        │ 0x17 解密失败？                     │
                        └─────────────┬───────────────────────┘
                                  是  │
                                      ▼
                         静默关闭——不发送任何告警。
                         TCP FIN 或 RST（取决于操作系统）。
```

任何无法建立的 Pre-Auth 回落——全局/每 IP 并发耗尽、IP 处于冷却、上游不可达——都会落到图顶部同一个 `emit_indistinguishable_close`，因此所有限额耗尽的结果共享同一种可观测行为（§5.2）。

## 8. Session 配置

`session` 块（可选，位于客户端 outbounds 和服务端 inbounds 的 `settings` 下）控制每个 Session 的行为：

| 字段　　　　　　　　　　 | 类型　　　　 | 默认值　　　　　 | 说明 |
|---|---|---|---|
| `max_streams_per_session` | usize　　　 | 256　　　　　　　| 每个隧道 Session 最大并发多路复用流数。 |
| `idle_timeout_secs`　　　| u64　　　　 | 75　　　　　　　 | Session 空闲拆除超时，**常量、无抖动**（nginx `keepalive_timeout` 默认值）。 |
| `traffic_script`　　　　　| optional string array |（嵌入式默认）　 | 声明式流量脚本，控制握手完成后数据包的行为（§3.5）：一个可选的 `stop=N` 条目加带索引的规则 `i=L:lo-hi,D:d,F:f`。规则按 `packet_seq % N` 循环应用直到 `stop`，随后以 6 包平滑融合窗口过渡至 Markov 机。示例：`["stop=4", "0=L:200-250,D:0,F:0", "1=L:300-400,D:2.0-0.5,F:0"]`。`D:` 的第一个数字是**中位数毫秒**。格式错误的脚本在启动时触发非致命警告并回退至嵌入式默认；另有五类语义警告（`F:m>0`、规则可能落入 `L1`、跨 MTU、`stop` 周期性、`post_script_shaping="off"`）见 §8。参考脚本见 `REFERENCE_TRAFFIC_SCRIPT`。 |
| `post_script_shaping` | optional string | `"markov"` | 脚本后整形模式（§3.5）。`"markov"`（默认）：融合窗口 → Markov 机。`"off"`：脚本用尽后按积压精确尺寸发出，零延迟、无 Fake 帧。非法取值在启动时触发非致命警告并按未设置处理。 |

嵌入式默认脚本（以 `traffic_script` 配置语法展示）：
```
stop=6
0=L:200-250,D:0,F:0
1=L:180-220,D:1.5-0.6,F:0
2=L:250-350,D:0,F:0
3=L:300-400,D:2.0-0.5,F:0
4=L:200-300,D:0,F:0
5=L:400-600,D:3.0-0.7,F:0
```

> 规则 2 与 4 此前是 `F:1`，现已全部置 0（原因见 §3.8）。

### `D:` 的取值语义

`D:` 的第一个数字是**中位数毫秒**，两种写法一致：`D:2.0` ≡ `D:2.0-0.5`（后者显式给出对数空间标准差）。内部存的是 `mu_ms = ln(中位数)`。

此前双参数写法把第一个数字**直接**当作对数空间的位置参数，于是 `D:1.5-0.6` 的实际中位数是 `exp(1.5) = 4.48 ms` 而不是 1.5 ms —— 照本节的配置语法抄写内嵌默认，会得到 **3.0×**（`D:1.5-0.6`）到 **6.7×**（`D:3.0-0.7`）的延迟。两种写法现已统一。

解析期还加了上界：中位数 ∈ (0, 500] ms、sigma ∈ [0, 2.0]。sigma 的上界同样必要——`D:2.0-5.0` 的中位数合法，但正态尾部能把单次采样推到中位数的 `e^20 ≈ 4.9×10⁸` 倍（数天）。此前 `D:1000-0.5` 会让 `exp(1000)` 溢出为 `inf`，`(inf * 1000.0) as u64` 在 Rust 中饱和为 `u64::MAX` µs ≈ **58 万年**，连接永久挂死。

### 配置校验的语义警告

`validate_traffic_script` 除解析外还检查五类会制造判别特征的配置，命中即非致命警告（**不**升级为解析失败——解析失败会回退内嵌默认，等于把这个部署重新塞回「全世界同一份默认」的群体，而那正是自定义脚本存在的唯一理由）：

1. `F:m > 0`（见 §3.8）
2. 规则随机化后可能落入 `L1`：判据是 `len_lo ≤ 161`。注意 `randomize_script` 的 ×0.85 缩放经 `as usize` **截断**，161 与 160 落到同一个值，**162 才是第一个安全值**（详见 §9.6）
3. 规则长度可能超出单个 MTU 分段（载荷 + 24 > ~1400）
4. `stop` 远大于规则数 ⇒ 在观测窗口内注入周期性自相关
5. `post_script_shaping = "off"` ⇒ `stop` 之后明文长度直接映射线速长度

### 参考脚本

`kanotls_config::script::REFERENCE_TRAFFIC_SCRIPT` 给出一组满足全部约束的示例取值，并附带一套可照做的 `tshark` 推导流程（抓取你想模仿的真实站点在外层握手之后的前 25–30 条应用数据记录，按 `载荷 = tls.record.length − 19` 换算，取 p10–p90 分位数填 `L:`，相邻记录时间差的中位数填 `D:`）。

**它是模板，不是标准答案。** 脚本的价值在于**跨部署的群体去聚类**（§9.10）——如果所有人照抄这一份，它立刻变成新的群体特征，与内嵌默认没有区别。而论文的判别量（首 burst、burst 结构、TCP 分段边界、往返次数）由 shaper 的硬编码逻辑保证，**不受脚本控制**：脚本写错只会更差，写对也不会更好。

脚本规则用尽后（通过平滑融合窗口衔接进入 Markov 机），TrafficShaper 的 Markov 状态机（§3.4）在连接剩余生命周期中掌管尺寸与延迟策略。Markov 转换参数无配置暴露——它们源自待发送缓冲区压力通过概率 `p_bulk` 渐变且方向对称。

## 9. 设计论证记录：被推翻的判断

本节记录那些**看起来对、实际会让伪装变差**的判断，以及推翻它们的依据。

之所以单列一节：这些结论的共同点是「直觉给出的方向与正确方向相反」。它们在实现里表现为几行不起眼的代码，但每一条都是在一次真实的错误尝试之后才确立的。后来的维护者若不知道这些论证，最可能做的恰恰就是把它们改回错误的那一侧。

本节引用的检测器指 USENIX Security 2024, Xue et al., *Fingerprinting Obfuscated Proxy Traffic with Encapsulated TLS Handshakes*（下称「论文」），它在真实 ISP 流量上评测，FPR 对齐推定的 GFW 阈值。

### 9.0 两条并列的原则

1. **能被稳定识别 = 会被封。** 任何跨连接恒定、可 memcmp 命中的特征都是致命的。
2. **全随机 = 会被封。** 如果真实实现在某个维度上是**恒定**的，那么我们在该维度上随机化，本身就是判别特征。

第 2 条常被忽略，而本节一半以上的条目源自违反它。判定一处该不该随机化，唯一的问题是：**真实的 Firefox / nginx 在这里变不变？**——不是「怎样更随机」。

### 9.1 检测器只在连接**出生时**判一次

论文的分类器要求观测到 SYN 与 SYN-ACK，只取**前 25 个承载数据的 TCP 包**，并丢弃包数不足的流。

⇒ **一条隧道连接只被采样一次，此后终生不再被采样。** 主导杠杆因此不是「流如何分布」，而是**「一共创建过多少条隧道连接」**：`P(被检出) = 1 − (1−TPR)^N`。TPR ≈ 0.15 时，N=1 → 15%，N=4 → 48%。

这条重新定义了连接池的目标：**把流集中到少数长连接上，不是为了性能，是为了减少被采样的次数**。`streams_per_connection_target` 取 `max_streams_per_session` 而非一个更小的值，原因在此。

**但它同时打开一个弱点**：正常 HTTPS 连接一辈子只有**一次** TLS 握手；一条承载 256 条流的隧道**一生有 256 次内层握手**散布在生命周期里。审查者把观测窗口挪到流中段的成本与看开头完全相同。因此每条新流的首个数据记录必须与连接的首个数据记录受同样的保护——这两件事必须成对存在，否则集中流反而放大暴露面。

### 9.2 burst 由方向改变**或** ≥3×RTT 的间隔打断

论文 §6.2 原文：聚合「1) 同方向 **且** 2) 到达间隔小于 3 倍估计 RTT」的连续包。

曾经的误解是「只有方向改变能打断 burst，时间间隔不算」。实际两个条件并列。但由此推出的「用停顿替代方向改变」方案**仍然是错的**，见 §9.7。

典型 RTT 20–200 ms ⇒ 打断阈值是 **60–600 ms**，而流量脚本 `D:` 的合理量级是 1–5 ms。所以 **`D:` 改变包序列（3-gram 的输入），但打不断任何 burst（Mahalanobis 的输入）**。

### 9.3 不能压制论文列出的全部 5 个高判别力 3-gram

分类器的负样本是**剥掉外层握手之后的正常 TLS 流**。而正常 HTTPS 的应用数据本来就大量产生 `(−L4,−L4,−L4)`、`(−L4,−L4,−L3)`、`(L2,−L4,−L4)`——那不过是「请求 → MSS 分段的响应 → 残尾」。论文 Table 2 的 `Distinc.` 是 **TLS-vs-非TLS** 的判别力，不是「含嵌套握手 vs 普通应用数据」的。

实测坐实了这一点：早期实现的下行**从不产生满 MSS 包**，一个 4 KB 响应被切成约 13 条 sub-MSS 记录。**一条下行永远没有 1460 字节段的 TLS 连接，比产生它们更异常。**

因此口径是：
- **零容忍**只针对编码「嵌套握手往返」的两个：`(L2,−L4,L1)` 与 `(−L4,L1,−L1)`，共同形态是「对端大 burst → 本端小包」，正常 HTTPS 应用数据不会这样；
- **反向断言** bulk 下载**仍然要**产生 `(−L4,−L4,−L4)`，防止过度整形。

`crates/session/src/session/tests.rs` 里两类断言并存，删掉任何一类都会让另一类失去意义。

### 9.4 客户端的两个 X25519 份额必须是**同一个**密钥

`key_share` 里 X25519（0x001d）份额与 X25519MLKEM768 混合份额尾部的 32 字节，在真实 Firefox 中**逐字节相同**——NSS 3.103 (Bug 1902119) 「reuse X25519 share when offering both X25519 and Xyber768d00」。捕获模板中该 32 字节恰好出现两次，可直接验证。

于是「为两处各生成一个独立的真实 X25519 密钥」会制造一个**比它修掉的更强**的判别器：真实 Firefox 两者恒等，我们恒不等 ⇒ **单连接、零误报的 32 字节 memcmp**。

而「用 `fill_bytes` 填随机字节」同样错，但错在另一头：真实 X25519 公钥是 mod 2^255−19 的小端 u 坐标，**最高位恒为 0**，随机字节有一半概率置位。

正解是**每连接生成一个真实密钥、写入两处**。

### 9.5 GREASE ECH 的 `enc` 恰恰**应当**是随机字节

与 §9.4 相反。捕获的 Firefox ECH GREASE 扩展中 `enc` 的第 31 字节最高位**为 1** ⇒ 它不可能是真实的 HPKE 封装公钥 ⇒ NSS 对 GREASE ECH 的 `enc` 就是填均匀随机字节。

所以此处必须 `fill_bytes`，**不要**「顺手修正」成真实密钥。`ech_grease_fields_are_uniform_random_not_x25519_keys` 断言 `enc` 的 MSB 无偏，正是为了让这种「修正」在 CI 变红。

同时 `config_id`（1 字节）逐连接随机、`payload`（239 字节）逐连接随机，但**全部长度字段恒定**——长度是确定性计算出来的，随机化长度会触发原则 2。

### 9.6 脚本规则的 L1 安全下界是 `len_lo ≥ 162`，不是 161

`randomize_script` 对每条规则的长度乘逐连接 `U[0.85, 1.20]`，线速尺寸 = 载荷 + `MIN_DATA_WIRE_LEN`(24)，而 L1 是**闭区间** [1, 160]：

```
len_lo=160: 160×0.85=136.00 → as usize 136 → 线速 160 → L1
len_lo=161: 161×0.85=136.85 → as usize 136 → 线速 160 → L1   ← 截断
len_lo=162: 162×0.85=137.70 → as usize 137 → 线速 161 → L2
```

`as usize` 的截断使 161 与 160 落到同一个值。**162 才是第一个安全值。**

一条 L1 类的本端记录若紧跟对端的大 burst，就精确复现判别力最高的 `(L2,−L4,L1)`。因此除了配置期的 lint 警告，`script_policy` 还有一道**硬钳制**——警告拦不住已经发出的记录。

### 9.7 「用 ≥3×RTT 的停顿替代方向改变」省不下任何往返

粗筛是合取式 `RT < 2.5 AND FirstBurst < 300`，而首 burst 的压制依赖一次方向改变，看起来抬高了 RT。由 §9.2 似乎可以改用停顿来打断 burst 而不增加交替。

**但对端的应答是它自己发的，不管我们等不等，那次方向改变都会发生。** 换成时间间隔一次往返都省不下来，RT 完全不变——而那是该方案唯一声称的收益。

其次，3×RTT 是**审查者按它自己的 RTT 估计**算的（从 TCP 握手估），我们从隧道握手估，停顿可能根本达不到它的阈值；方向改变则是无条件的。

### 9.8 合并 flush 边界对论文特征**无可测量收益**

「小控制记录各占一个 TCP 段」看起来是高包数与残留 gram 命中的根因。对照实测（40 条连接/场景，合并开关各测一遍）显示：总包数与窗口内方向改变次数**全部落在轮次间方差内**。

原因：单流场景下同刻排队的内容本来就很少（写请求被 RTT 与应用节奏自然拉开）；而零延迟源站下的残留 `(L2,−L4,L1)` 成因是**对端内核**把开场 flight + SYNACK + 响应体合并成一个大分段——**我方的 flush 边界改不了别人的内核**。

机制本身正确（真正同刻排队时确实合并）且更接近 NSS/BoringSSL，因此保留；但它属于「保真」而非「收益」。同理，**合并 flush 不会降低 RT**：它只拼接同方向相邻写，永不减少方向交替；固定 25 包窗口内包数变少 ⇒ 窗口覆盖更长时间跨度 ⇒ 交替次数只会持平或上升。

### 9.9 数据记录与控制记录按尺寸**刻意**不可区分

曾有一个论证以「所有小于约 194 字节的记录都可被无歧义判定为控制类」为前提。该前提不成立：`markov_policy` 的 `InteractiveControl` 分支**故意**让数据记录复用控制帧的尺寸池，bulk 迟滞尾包与 `post_script_shaping = "off"` 也能产出任意小的数据记录。

观察者无法按尺寸干净地划分 control/data——**这正是设计目标**。任何依赖「按尺寸区分两类记录」的论证都是无效的。

### 9.10 流量脚本的定位：群体去聚类，不是结构性防御

论文的判别量（首 burst、burst 结构、TCP 分段边界、往返次数）**基本都由 shaper 的硬编码逻辑保证**：连接首记录的尺寸窗口抢在脚本之前；方向让出由对端按 H2 语义回 SETTINGS-ACK 提供；`stop` 与融合窗口之后交给硬编码的截断正态。脚本在 25 包窗口里实际只管辖其中一小段。

脚本真正的价值是**对抗群体聚类**：若全世界都跑同一份内嵌默认，该默认的尺寸/IAT 分布本身就是一个可拟合的群体特征，一次拟合命中全部默认部署。

**但这是双刃剑。** 脚本只有在你选的分布**同样是某个真实应用的分布**时才有帮助；选一个不像任何真实应用的分布，只会让这个部署从「混在群体里」变成「一个独一无二的怪异分布」。

由此推出：**参考脚本必须以「模板 + 推导方法」形式存在**（见 `kanotls_config::script::REFERENCE_TRAFFIC_SCRIPT` 的文档注释）。如果所有人照抄它，它立刻变成新的群体特征——和内嵌默认没有区别。

### 9.11 为掩盖常量而引入的随机化，必须随那个常量的消除一并撤销

`emit_indistinguishable_close` 曾在关闭前随机等待 200–3000 毫秒。它是有理由引入的：当时「限额耗尽」是瞬时关闭、「读超时」是恒定时刻关闭，两个可测常量需要被抹平。

但后来两处修复分别消除了那两个常量本身——输入驱动的失败全部改走透明转发，读超时的截止时间也压到了让上游主导的量级。**掩护对象消失之后，掩护本身就退化成了唯一剩下的特征**：真实服务器不会在均匀随机延迟之后关闭。

所以每当一处「为掩盖 X 而引入的随机化」中的 X 被别的修复消除时，必须回头把这处随机化一并撤销。否则它会以「历史上曾经必要」的名义长期留存，而它现在唯一的作用是制造原则 2 意义上的判别特征。

### 9.12 硬编码取值的正确处理不是随机化，而是对齐到真实来源

`FIRST_RECORD_PAYLOAD_LO/HI`、`next_data_record_payload` 的分布参数、`MARKOV_DELAY_SIGMA`、H2 开场 flight 的尺寸序列、WINDOW_UPDATE 阈值、PING 空闲阈值——这些全是全球统一的常量。

它们**应该**是常量（原则 2：真实实现的尺寸决策代码就是编译期常量）。问题因此不是「要不要随机化」，而是：**这套硬编码分布看起来像某个真实实现，还是像不存在的东西？**

所以每一处硬编码取值都必须能指认一个真实来源：Firefox 的 keepalive 600 s / 1 s / 4 probes、nginx 的 `keepalive_time 1h`、Firefox 的 `ping-threshold = 58 s`、Firefox 的 `kInitialRwin = 12 MiB`（取半得 WINDOW_UPDATE 阈值）、H2 的 SETTINGS / WINDOW_UPDATE / PING / GOAWAY 帧尺寸、捕获的 Firefox 15 个扩展。**「全球统一」在这里不是缺陷，只要它统一到的是真实的东西。**

同理，`H2_GHOST_VARIANTS` 的变体选择改为**逐进程**而非逐连接：真实 Firefox 的 SETTINGS 是编译期固定的，同一浏览器的每条连接都发相同尺寸；逐连接抖动等于在一个真实恒定的维度上制造方差。它也**不**按 PSK 派生——那会让线速长度变成密钥材料的函数，且把一个部署的全部客户端塌到同一变体。
